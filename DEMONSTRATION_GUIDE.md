# Demonstration Guide (5–7 minutes)

## Before the demo
1. Install Python and project requirements using README.md.
2. Download the Kaggle CSV and put it in `data/multi_platform_social_sentiment_evolution.csv`.
3. Run `streamlit run app.py`.
4. Keep the terminal open while the app is running.

## Suggested presentation sequence

### 1. Explain the extension (30–45 seconds)
“My Experiment 1 case study was social media analytics for trend detection and virality prediction. I extended it by implementing a PySpark processing pipeline, platform/topic/sentiment analytics where supported by the dataset, optional Random Forest classification, and an interactive Streamlit dashboard.”

### 2. Show the dataset and data quality (1 minute)
- Open “Data quality and detected schema”.
- Point out source columns and recognized fields.
- Show rows before/after duplicate removal.
- Explain that missing categories are marked `Unknown`.
- Mention any fields the Kaggle CSV does not contain.

### 3. Show platform and topic analysis (1 minute)
- Use filters if the relevant fields exist.
- Explain that PySpark `groupBy` and aggregation calculate counts.
- Download one aggregate CSV to demonstrate that outputs are generated by code.

### 4. Show sentiment and engagement (1 minute)
- Show sentiment distribution only if the source includes a sentiment label.
- Show engagement comparisons only if numeric engagement columns are available.
- Do not claim a missing metric was analyzed.

### 5. Show time trend (30–45 seconds)
- Explain that the chart groups records by date if a recognizable timestamp exists.
- State clearly that the current dataset is static, not a live stream.

### 6. Run machine learning (1–2 minutes)
- Click “Train/evaluate Random Forest model”.
- Explain the target chosen by the app:
  - existing sentiment label, if available; otherwise
  - Low/Medium/High engagement categories, if likes, shares and comments are present.
- Explain accuracy and weighted F1 as held-out test-set metrics.
- Mention that predictors exclude raw engagement values when predicting engagement categories to reduce target leakage.
- If the model is unavailable, explain the displayed reason; do not invent metrics.

## Common viva questions

**Q: Why is this a Big Data project?**  
A: It applies a scalable processing framework, PySpark, to structured and semi-structured social media records and demonstrates data cleaning, aggregation and optional ML. A local run illustrates the pipeline; it does not prove multi-node scaling.

**Q: What are the 3Vs/5Vs here?**  
A: Volume is the number of records; Variety is the mix of numeric, categorical, timestamp, text and sentiment fields; Velocity is relevant to continuously arriving engagement data but is not implemented as live ingestion in this version. Veracity is addressed through data-quality checks. Value comes from actionable trend summaries.

**Q: Why PySpark instead of only Pandas?**  
A: Spark DataFrames support distributed transformations and can scale beyond a single machine. This demonstration uses Spark's local mode.

**Q: Is it real-time?**  
A: No. It analyzes a downloaded CSV snapshot. Live streaming is future scope.

**Q: Did you implement Hadoop/HDFS?**  
A: No. The current implementation uses local PySpark. HDFS, YARN and related components were discussed in Experiment 1 and can be added in a cluster-based extension.

**Q: How is the model evaluated?**  
A: The application uses a deterministic 80/20 random split and reports accuracy and weighted F1 from the held-out test split. The actual values must be read from the run.

**Q: What if a column is missing?**  
A: The dashboard checks available fields and skips charts or modeling tasks that cannot be supported. It does not fabricate values.
